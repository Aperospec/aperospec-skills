# Aperospec Team Productivity Protocol

This document defines how the 7 roles operate as a productive system.

The goal is not stylistic consistency.

The goal is:

> stable throughput with low drift, low rework, and high-quality final output.

## 1. Productive Team Definition

The Aperospec team is productive only when all of the following are true:

- each role does one job well
- each handoff is explicit
- each artifact is usable by the next role without reinterpretation
- failures are traced to the correct stage
- rework is narrow, not global
- locked assets stay protected
- the Final Deck reaches user review without collapsing into generic output

If one role is strong but handoff is weak, the team is not productive.

If the final deck looks good once but cannot be repeated reliably, the team is not productive.

## 2. Operating Model

The operating model is:

`User -> Runtime -> Injection(optional) -> Project -> Cinema -> ConceptDeck -> VisualDirector -> Rendering`

Productivity depends on two things:

1. each stage must output a usable artifact
2. Runtime must decide quickly and correctly when to continue, pause, or rework

## 3. Team-Level Failure Types

The team has six primary failure types.

### Failure A: Role Drift

One skill starts doing another skill's job.

Examples:
- Project starts writing narrative scenes
- Cinema starts deciding page rhythm
- ConceptDeck starts doing poster execution
- VisualDirector rewrites concept meaning

### Failure B: Handoff Weakness

The next skill receives an artifact that is technically present but operationally weak.

Examples:
- CWP is too abstract to translate
- NWP is too vague to sequence
- CDP is too loose to visualize

### Failure C: Lock Violation

Confirmed names, structures, or client-fixed assets are altered downstream.

### Failure D: Rework Explosion

A local problem causes the whole pipeline to restart unnecessarily.

### Failure E: Rendering Collapse

Upstream logic is valid, but Stage 5 weakens the work into generic slide output.

### Failure F: Runtime Mismanagement

Runtime fails to escalate, reroute, or protect boundaries correctly.

## 4. Productive Handoff Standard

Each handoff is productive only when the receiving role can continue without inventing upstream logic.

### CWP is productive when:

- root cause is concrete enough to support translation
- driving forces create real pressure
- contradiction contains narrative tension
- triggers are perceptible, not abstract slogans

### NWP is productive when:

- the world is enterable
- emotional environment is specific
- the conflict is dramatic enough to drive sequence
- scene potentials are cinematic enough to become deck cognition

### CDP is productive when:

- each page has one real concept unit
- sequence and rhythm are clear
- atmosphere direction is actionable
- the visual role of each page is understandable

### VDP is productive when:

- content fidelity is intact
- page energy is classified
- Hero Image direction is strong enough to render
- composition logic is clear enough for Stage 5 execution

## 5. Team Acceptance Gates

The team should use four acceptance gates.

### Gate 1: Upstream Validity

Before leaving Project:
- CWP is not abstract filler
- CWP is not narrative
- CWP is usable by Cinema

### Gate 2: Narrative Validity

Before leaving Cinema:
- NWP is not just atmospheric writing
- NWP creates real conflict and emotional world
- NWP is usable by ConceptDeck

### Gate 3: Deck Validity

Before leaving ConceptDeck:
- CDP is not a mood board
- page sequence is cognitively actionable
- CDP is usable by VisualDirector

### Gate 4: Visual Validity

Before leaving VisualDirector:
- VDP does not invent copy
- VDP does not flatten page energy
- VDP is renderable without redesign

## 6. Rework Discipline

The team becomes unproductive when every problem becomes a full restart.

Required discipline:

- Project problems return to Stage 1
- Narrative translation problems return to Stage 2
- Deck sequencing problems return to Stage 3
- Visual execution problems return to Stage 4
- Rendering-only problems return to Stage 5

Runtime owns this discipline.

## 7. Escalation Discipline

When a skill cannot continue faithfully, it must escalate.

It must not:
- hide upstream weakness
- invent missing content silently
- compensate by drifting into another role

Escalation is a productivity behavior, not a failure.

## 8. Team KPI

If you want to judge whether the team is becoming more productive, watch these signals:

- fewer cross-role rewrites
- fewer full-pipeline restarts
- stronger locked-name preservation
- cleaner artifact handoff
- stronger Stage 5 fidelity
- less corporate PPT degradation
- faster path from topic to reviewable final deck
